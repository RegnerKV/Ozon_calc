# Диагностика API для Windows

Отдельный `OzonApiDiagnostics.exe` для установленной Windows-версии
`v0.3.0-rc.3`. Установка Python не требуется. Приложение Ozon Profit не
обновляется; отдельный раздел «Реклама» не добавляется. Исходная ветка main
уже содержит более поздний интерфейс; этот диагностический файл его не запускает.

## Запуск

1. Распакуйте `OzonApiDiagnostics-Windows.zip` в отдельную папку.
2. Запустите `OzonApiDiagnostics.exe` под той же учётной записью Windows,
   в которой сохранены подключения Ozon Profit.
3. Выберите новое имя JSON-файла вне папки данных приложения. Существующий
   файл не перезаписывается. Дождитесь сообщения о сохранении отчёта.

По умолчанию читаются `%LOCALAPPDATA%\OzonProfit\seller.credentials` и
`%LOCALAPPDATA%\OzonProfit\profit.db`. Поддерживается существующий
`OZON_PROFIT_DATA_DIR`. Seller расшифровывается через Windows DPAPI из файла;
Performance — из `secure_items/performance`, формат `DPAPI:`. Эти форматы
сверены с кодом линии RC3 (`fa33e92`). Ключи повторно не вводятся.
Сохранённые через веб-пароль подключения имеют другой формат: диагностика
отмечает `web_password_required`, не просит ключи и не меняет хранилище.

SQLite открывается с `mode=ro` и `PRAGMA query_only=ON`, без создания базы,
инициализации схемы, импорта и пересчёта. Из базы читаются только метаданные
таблиц, подключение Performance и сопоставление контрольного артикула с SKU.
Финансовые таблицы и история заказов в базе не запрашиваются. Доступен запуск
при работающем приложении; при занятости/ошибке чтения это будет отражено в JSON.

Период фиксирован: **13.10–09.11.2026 включительно, московские даты**.
Контрольный артикул — `подвеска_наличник`. При наличии Seller проверяется
живое сопоставление SKU; при невозможности используется сохранённое.

Проверки:

- Заказы: `/v3/posting/fbo/list`, `/v4/posting/fbs/list`, по одному отправлению
  магазина; без экспорта содержимого, покупателей и финансовых данных.
- Остатки: `/v4/product/info/stocks` для артикула и `/v1/analytics/stocks`
  для его SKU. Это текущие остатки, не история на даты контрольного периода.
- Поиск: `/v1/analytics/product-queries/details`, первая страница до 15 запросов
  на SKU; сохраняется только количество непустых известных полей, без текста запросов.
- `/v1/analytics/data`: отдельно `ordered_units`, `hits_view`, `hits_tocart`,
  группировка `sku/day`, первый найденный SKU, первая страница до 1000 строк.
  Интервал между запросами — не менее 61 секунды. Поэтому диагностика занимает
  несколько минут. Наличие нуля отличается от отсутствующего значения.
- Performance: получение токена, список кампаний со всеми состояниями,
  `POST /api/client/statistics/json` с `groupBy=DATE` по одной CPC-кампании,
  проверка готовности и `GET /api/client/statistics/report` по UUID.
  Ссылки скачивания из ответа игнорируются; перенаправления запрещены.
  CPO и CPM не включаются в проверку кликовых расходов.

В одной проверке — до 20 CPC-кампаний (параметр `--max-campaigns 1..100`),
до 20 страниц списка кампаний. Ограниченность выборки явно отмечается.
Генерация отчёта не меняет кампании, ставки и бюджеты, но расходует квоту
выгрузок Performance. Ожидание — до 12 опросов с паузой 5 секунд плюс время
самих запросов. Незавершённый отчёт отмечается как pending, следующие выгрузки
не запускаются. Не запускайте несколько диагностик одновременно и не обновляйте
Performance в приложении во время этой проверки. В случае pending повторите позже.

## Что означает JSON

Это диагностика доступа и структуры выборки, не полный отчёт продаж.
HTTP-ответ и распознанная структура отмечаются раздельно. HTTP 400/403/404
не устанавливают тариф или необходимость Premium Plus; подписка остаётся
`unknown`. Пустой ответ не доказывает отсутствие доступа или нулевые показатели.
Неизвестная структура отмечается как `unrecognized`, не подменяется нулями.
Доступность отдельного поля не доказывает полноту выгрузки за период.

В JSON нет ключей, токенов, Client ID, UUID, названий кампаний, SKU-идентификаторов,
текстов ошибок провайдера, содержимого заказов и финансовых операций.
Сохраняются только фиксированные имена методов/полей, HTTP-коды, состояния,
число строк и наличие числовых значений. Значения метрик API не выгружаются.
Известные форматы Performance `rows` и `campaign-id → report → rows`
проверяются на контрольный SKU и дату. Иные форматы остаются нераспознанными.

В отдельном блоке `owner_reference_not_api_result` записаны **данные владельца**:
примерно 1427 рекламных кликов, 64 добавления в корзину, примерно 2059 ₽
только расходов за клики; 11 реализованных изделий из всех источников.
Число заказов, приписанных рекламе, неизвестно (`null`). Конверсия не вычисляется.
`orders` Performance и `modelOrders` проверяются отдельно, не подменяют 11 продаж.
Seller `ordered_units` означает заказанные товары, не реализацию и не атрибуцию.

## Схемы и границы проверки

Официальные источники: <https://docs.ozon.ru/api/seller/> и
<https://docs.ozon.ru/api/performance/>. 10.11.2026 прямой доступ из облачной
среды отклонён её прокси. Вместо прямой проверки использованы опубликованные копии:

- `artefactby-ozon-seller-api@0.19.1` из npm; SHA-512 integrity архива проверена.
  В схеме `ordered_units` доступна всем, для `hits_view`/`hits_tocart` описан
  Premium Plus. Фактический результат конкретного ключа проверяется отдельно.
- `DragonSigh/ozon-performance-api-docs`, commit
  `b562eba5539dd882e60644a81b67346756e9c090`: статистика, кампании, лимиты.
- Дополнительная сверка типов: `QuoVadis86/go-ozon-performance`, commit
  `3ece64b278f23abf23b025a20340f92fd149862c`.

Проверка не утверждает наличие/отсутствие Premium Plus на аккаунте.
Реальный доступ можно установить только после запуска EXE на Windows владельца
с уже сохранёнными подключениями. В облачной машине этих подключений нет.
Сертификаты TLS проверяются; Windows использует системное доверие через truststore.

## Разработчику и сборка

```text
python -m pytest -q
python -m pip install pyinstaller==6.16.0
python -m PyInstaller --noconfirm --clean --onefile --console --name OzonApiDiagnostics --collect-all truststore diagnose_api.py
python scripts/smoke_diagnostics_windows.py
```

Собирать EXE и запускать последнюю проверку нужно на Windows с Python 3.12.
Workflow **Windows API diagnostics** выполняет полный pytest, сборку EXE,
проверку настоящего DPAPI на синтетических данных, неизменности базы/ключей,
безопасного JSON и отказа от перезаписи отчёта. Затем создаёт ZIP и SHA-256.
Артефакт `OzonApiDiagnostics-Windows` появляется только после успешных проверок.
Этот workflow не публикует релиз и не обновляет основное приложение.

Для локальной проверки без сети:
`python diagnose_api.py --offline --output diagnostics.json`.
`--data-dir` позволяет явно указать папку существующей базы без изменения настроек.
Успешный offline-запуск проверяет чтение подключений, но **не доступ к Ozon API**.
