# Прибыль по данным Ozon API

Пользователь подтвердил успешное получение начислений за известный период и совпадение итоговой суммы с Excel. Далее требуется проверить детализацию продаж и себестоимость. Сама итоговая сумма не подтверждает количество изделий, налоги или чистую прибыль.

## Включение в приложении

1. Обновите страницу. В «Подключение Ozon» выберите нужный период и свои схемы FBO/FBS. Снимите флажок «только финансовые начисления» и загрузите данные, чтобы получить артикулы и состав отправлений.
2. При необходимости раскройте «Загрузить себестоимость для товаров API»: загрузите один файл «Себестоимость.xlsx», проверьте изделия и дату действия, сохраните. Синий «Наличник» сопоставлен по подтверждению владельца; оценки обеих «Малин» по «Рыбе» останутся помеченными как примерные. Значения берутся из файла, не из кода.
3. В блоке «Прибыль по данным API» проверьте налоговую базу, начисления, реализацию, стоимость, резерв налога и предварительную прибыль. Для сравнения с прежней методикой используется «Только реализация». Это воспроизведение допущения, не правовое подтверждение налога.
4. Если структурных ошибок нет, отметьте замену Excel и нажмите «Включить прибыль API». Затем откройте «Обзор» и выберите период. Следующие успешные загрузки из кнопки обновления и расписания пересчитывают прибыль автоматически.

## Защита от ошибок

Для каждого accrual_id сумма разобранных компонентов обязана точно совпасть с total_amount. В наблюдаемом формате by-day поле sale_amount включает баллы и партнёрские выплаты. Покупательская реализация выделяется как sale_amount − bonus − coinvestment; затем bonus/coinvestment добавляются отдельными видами дохода ровно один раз. Итоговая комиссия commission используется как комиссия, без повторного вычитания из неё возмещений; при отсутствии итоговой комиссии используется указанная исходная sale_commission. Для доставки используется total_accrued либо услуги, если итог не передан. Эти два уровня не складываются. Произвольная разница не записывается в корректировки, а блокирует переход.

Количество сначала проверяется по sale_amount / seller_price, затем по покупательской реализации / sale_price, либо по составу отправления при единственной положительной продаже. Поддерживаются нулевые покупательские продажи, полностью покрытые возмещениями: стоимость всё равно списывается. Отдельное начисление баллов с sale_amount=0 не создаёт фиктивный возврат выручки.

Частичное количество возврата без точной цены не угадывается. Количество положительных продаж с учётом уже учтённых продаж вне периода не может превысить состав известного отправления. API не восстанавливает физический запас по одному лишь возврату денег.

Артикул определяется по составу отправления, сохранённому соответствию SKU→артикул или запросу POST /v3/product/info/list. Учитываются основной SKU и sources[].sku, только при совпадении с запрошенными идентификаторами; позиция товара в ответе не используется для угадывания. Соответствия сохраняются при импорте оригинальных Excel и загрузке отправлений. Для поиска заказов запрашивается также 31 день до начала финансового периода; более старые заказы могут требовать расширения диапазона. Справочник стоимости с датами продолжает действовать. При неизвестной стоимости числовая прибыль не показывается, включение API блокируется. Примерная стоимость допускается с отметкой предварительного результата и не заменяется вымышленным точным числом.

Период API должен быть покрыт последней полностью успешной финансовой загрузкой. До первого включения API финансовая база и расчёт прибыли разделены. При включении заменяются только операции адаптера Ozon Excel и прежней проекции API за выбранный период. Общий ручной финансовый импорт блокирует включение до определения источника, чтобы не создать дубли. Ручные нулевые restock сохраняются.

Перед изменением прежние операции периода сохраняются в ledger_backups внутри личной SQLite-базы. Есть кнопка «Вернуть предыдущие операции периода и отключить автопересчёт API». Восстанавливаются операции, а не настройки налога/история стоимости. Повторный одинаковый пересчёт не создаёт лишних резервных версий. Внешняя резервная копия всей базы по-прежнему рекомендуется для недолговечного хранилища Community Cloud.

После включения API каждая успешная загрузка пытается пересчитать её период. Если новое начисление не разобрано, финансовые данные сохраняются для проверки, но прежние операции прибыли не заменяются. В обзоре появляется предупреждение, а дата успешного пересчёта прибыли не обновляется. Таким образом, дата загрузки и дата расчёта различаются.

## Ограничения

Подтверждённая прибыль не появляется автоматически: отчёты могут быть неполными, стоимость оценочной, а налоговая база и внешние расходы — не проверенными. Общие услуги остаются общими; результат заказа до этих услуг не равен окончательной прибыли заказа. Деньги для вывода рассчитываются отдельно по фактическому остатку и резервам.

Переход и автоматические исправления протестированы на вымышленных данных, включая форму включения и обзор. Реальный результат прибыли магазина после перехода требует отдельного сравнения с прежней сверкой в размещённом приложении. Успех загрузки начислений пользователем не выдаётся за подтверждение всех деталей расчёта.

Для уже загруженных начислений есть кнопка «Сопоставить SKU автоматически»: она запрашивает недостающие артикулы без повторной загрузки финансов. Если ошибки остались, «Скачать диагностику сопоставления» создаёт JSON по проблемным начислениям с числовыми компонентами и связями товаров/отправлений. Файл содержит финансовые данные и не предназначен для публикации; ключи, сырые ответы и покупательские данные не включаются.

Прежние проекции API, в которых sale_amount ошибочно считалась покупательской реализацией, помечаются требующими пересчёта. Их налог и прибыль не выдаются за актуальные. После пересчёта метка снимается для обновлённого периода; исходные записи сохраняются в резервной версии.
