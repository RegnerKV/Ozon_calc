# Ozon Profit 💎

Приложение для Windows 10/11 с русским интерфейсом в локальном браузере. Python и платный хостинг пользователю не нужны. База, стоимость товаров, история, настройки и план сохраняются в личной папке Windows; ключ Ozon защищён DPAPI текущего пользователя.

## Пять разделов

- **Обзор**: прибыль, реализация, начисления Ozon, стоимость, налог, реклама, рентабельность, динамика и результат товаров. Основная кнопка — «Обновить». Операции и ручные денежные резервы спрятаны в раскрывающиеся блоки.
- **Товары**: однократная загрузка Себестоимость.xlsx, история стоимости и редактирование. Сохранённая библиотека применяется к новым товарам; ручные значения не перезаписываются автоматически.
- **План продаж**: срок, товары, количество и прогноз чистой прибыли. Реклама — общий бюджет за клики в рублях плюс ставка за заказы: 0, 6, 8 или 10%. План сохраняется автоматически и не меняет реальные операции.
- **Реклама**: общие показы по дням, расходы за клики, история продвижения за заказ, сравнение условий по магазину и товарам. Данные API или импорт Excel/CSV сохраняются между запусками.
- **Настройки**: однократное подключение Ozon, обновления и налоги. Диагностика и прежние способы импорта доступны в дополнительных инструментах.

## Первый запуск Windows

Готовая проверенная beta-сборка: [OzonProfit-Windows.zip](https://github.com/RegnerKV/Ozon_calc/releases/download/v0.4.0-rc.2/OzonProfit-Windows.zip), около 115 МБ. Проверка Windows: [workflow](https://github.com/RegnerKV/Ozon_calc/actions/runs/42578561506). Распакуйте весь архив и дважды нажмите OzonProfit.exe. В настройках один раз введите Client ID и ключ Seller API на чтение, в товарах один раз загрузите себестоимость и проверьте дату. Дальше данные подхватываются автоматически.

Приложение хранит базу в `%LOCALAPPDATA%\OzonProfit\profit.db`, отдельно от папки EXE. Повторный запуск открывает уже работающий экземпляр. Закрытие вкладки не останавливает сервер; для завершения закройте консольное окно. Сборка не подписана цифровой подписью. Используйте собственный проверенный релиз, не отключайте защиту Windows.

## Расчёт и пределы

Начисления = сумма финансовых операций со знаком; предварительная прибыль = начисления − стоимость проданных изделий − налоговый резерв. По API покупательская реализация выделяется из sale_amount за вычетом bonus/coinvestment. Возмещения, итоговые комиссии и доставка не учитываются дважды. Каждый accrual_id обязан сойтись по сумме. При неизвестном составе или количестве предыдущая прибыль сохраняется, новая не подставляется корректировкой. Без стоимости активация расчёта блокируется; введённые владельцем стоимости приняты для расчёта.

Налоговые настройки предварительные, не являются расчётом ФНС. Прибыль не равна банковскому остатку и доступным деньгам для вывода. Сумма вывода определяется отдельно по фактическому остатку и резервам. Возврат выручки не означает восстановление физического товара в запасе. Основной учёт ведётся по датам начислений, общие расходы не распределяются по заказам автоматически.

Прогноз использует среднюю реализацию, возмещения и удержания по истории, стоимость на начало плана, общий бюджет за клики, ставку продвижения за заказы и налоги. Реклама исключается из исторического вклада и добавляется в сценарий ровно один раз. Для нового товара нужна ожидаемая цена; при отсутствии собственной истории используются средние условия магазина с отметкой оценки. Разовые компенсации/корректировки не переносятся в будущие продажи. Срок определяет темп, не умножает прибыль на количество дней. Это сценарий, не прогноз спроса.

## Разработчику

Существующий checkout `/workspace/Ozon_calc`; отдельный worktree не нужен.

```bash
python3 -m venv /workspace/ozon-venv
/workspace/ozon-venv/bin/python -m pip install -r requirements-dev.txt
/workspace/ozon-venv/bin/python -m pytest -q
/workspace/ozon-venv/bin/python launcher.py
```

Локальный сервер слушает только 127.0.0.1; телеметрия отключена. Web-режим по умолчанию требует app_password в Streamlit Secrets. На Linux ключ сохраняется зашифрованно с использованием этого пароля. Для постоянства после полной пересборки Community Cloud подготовлено опциональное приватное хранилище Supabase с зашифрованной копией SQLite; реальное подключение Supabase требует реквизитов владельца. В Windows Supabase не нужен. Пользовательские резервные копии исключают даже зашифрованный ключ API.

Workflow Windows application запускает тесты, PyInstaller и браузерную проверку настоящего EXE: экраны, DPAPI, единственный экземпляр, план и повторный запуск. ZIP публикуется как предварительный GitHub Release только после этих проверок. Не считайте один файл workflow доказательством успешной сборки: фактический результат указан в отчёте задачи.

Технические подробности: API_STATUS.md, API_MIGRATION.md, API_PROFIT.md, VALIDATION.md. Реальные Excel, базы, ключи и финансовые результаты не входят в исходники или релиз. Публичные тесты и скриншоты сборки используют вымышленные данные.

## Ошибка соединения с Ozon

Windows-сборка beta.3 использует системное хранилище доверенных сертификатов
Windows с обязательной проверкой HTTPS. Ошибки сертификата, прокси и тайм-аутов
показываются отдельно, без текста исключений, ключей и содержимого запросов.
В настройках доступна отдельная проверка соединения без импорта данных.
При обновлении закройте консоль старой версии и распакуйте новый архив целиком
в отдельную папку. Локальная база и ключ остаются в прежнем месте.

Проверка сборки выполняется на вымышленных данных; она подтверждает работу EXE,
но не доступность Ozon из сети конкретного пользователя. При неудаче обновления
сообщите безопасный код ошибки и имя метода; сам API-ключ присылать не нужно.

## Данные загружены, но расчёт не завершён

Дашборд рассчитывает выбранный период непосредственно по сохранённым данным API.
Ошибка сопоставления в другом месяце не скрывает доступный период. Это просмотр
без перезаписи учётных операций. Если не хватает исторической себестоимости,
начисления и реализация видны, а прибыль скрыта до уточнения стоимости; таблица
показывает артикул и дату продажи. При несопоставленных начислениях показываются
только исходная сумма начислений API и причины блокировки, без частичной прибыли.
«Последний месяц с данными» определяется по фактическим операциям, а не дате
окончания загрузки пустых дней. Все проверки используют вымышленные данные.

## Принятое владельцем правило для остатков ассортимента

Товары без собственной себестоимости автоматически получают полную стоимость
подвески «Рыба» из сохранённого справочника, включая упаковку. Для старых продаж
используется первое сохранённое значение «Рыбы», последующие изменения стоимости
применяются с соответствующих дат. Это принятое владельцем значение для учёта,
без флага оценочной стоимости; пояснение об источнике сохраняется в истории.
Прежние автоматические оценки по «Рыбе» переводятся на это правило. Собственные
стоимости товаров и другие ручные оценки сохраняются. Если позже задать
собственную стоимость, она имеет приоритет с выбранной даты. При отсутствии
стоимости самой «Рыбы» программа не придумывает число. Правило работает для
новых артикулов при обновлении каталога и для планирования продаж.

## План продаж и ДРР

История плана берётся из сохранённых данных API за выбранные даты, в том числе
когда весь диапазон ещё не перенесён в итоговый учёт. При неполном сопоставлении
причины показываются явно. Средняя цена и удержания своего артикула имеют
приоритет; для нового артикула нужны ожидаемая цена и средние условия магазина.
Бюджет за клики вычитается один раз целиком, а продвижение за заказы добавляется
отдельно как 0/6/8/10% от плановой реализации покупателям. Историческая реклама
исключена из средних удержаний. Бюджет в строках прогноза распределён по выручке;
это допущение плана, а не фактическая атрибуция. Другие разовые расходы
необязательны: например, фотосъёмка; оставьте ноль, если их нет.

Фактический ДРР = рекламные расходы с учётом возвратов / реализация покупателям
с учётом возвратов × 100%. В «Обзоре» показаны общий ДРР и ДРР артикулов.
Если часть рекламы не привязана к артикулу в исходных операциях, полный ДРР
артикулов не определяется: отдельно видна сумма без привязки. Она включена
в общий ДРР магазина. При отсутствии реализации процент не вычисляется.

## Обзор и подключение Performance

Периоды: текущий месяц по московской дате, полный прошлый месяц, последние
7/30 дней включительно и свои даты. «Налоги (4%)» используют ставку из настроек;
«Процент чистой прибыли» — прибыль / реализация покупателям × 100%.
График переключается между чистой прибылью и реализацией с учётом возвратов.
Денежная таблица показывает реальные знаки: плюс — поступление, минус — расход.
Баллы, отмены баллов и партнёрские выплаты сгруппированы как «Соинвест» только
в представлении; их отдельные налоговые категории сохранены. Возврат денег
покупателю отрицательный и не восстанавливает склад автоматически. Расшифровка
прочих услуг показывает фактические названия из API; при их отсутствии примеры
явно помечены как примеры. Раздел «Личные деньги» убран.

В «Настройки → Реклама — Ozon Performance API» сохраните отдельные Client ID
и Client Secret сервисного аккаунта, проверьте токен и нажмите «Обновить».
[Создать ключ](https://seller.ozon.ru/app/settings/api-keys?currentTab=performanceApi).
Рекламные реквизиты сохраняются зашифрованно; в чат их передавать не нужно.
Подключение проверено на тестовых ответах, а фактический JSON-отчёт и доступ
проверяются после ввода реквизитов владельцем. Статистика Performance применяется
к карточкам рекламы/ДРР, не вычитается повторно из финансовой прибыли. Различия
между источниками отмечаются предупреждением и требуют сверки. Отсутствующие
данные не выдаются за нулевые расходы. Подробности: PERFORMANCE_API.md.

## Реклама, вложенные расходы и товарный дашборд

Коды Seller `PayPerClick` и `Promotion` — рекламные расходы (оплата за клик и
продвижение за заказ). Они переклассифицируются из услуг, без второго вычитания
из прибыли. Исторические API-операции обновляются с резервной копией при
возможности полного сопоставления; просмотр выбранного периода также использует
новую классификацию. План исключает эти расходы из исторических удержаний перед
применением заданного бюджета. ДРР всегда считается относительно реализации
покупателям, не прибыли. Performance остаётся независимым источником сверки.

В основной таблице расходов встроены раскрывающиеся строки «Реклама» и «Прочие
услуги», с суммами и русскими названиями непосредственно внутри таблицы.
DefectFineErrors оставлен в скобках: перевод указывает штрафы/корректировки,
но не выдумывает конкретную причину. Все динамические подписи HTML экранированы.
Навигация — синие скруглённые плашки со значками, бренд без алмаза.

Под товарной таблицей выбирается артикул: прибыль за период и на штуку,
реализация, реклама, ДРР, стоимость, налоги и процент прибыли. Общий дашборд
от этого выбора не фильтруется. При отсутствии прямой связи общих услуг и
рекламы с SKU общие расходы распределяются по положительной реализации.
Сумма товарной прибыли сходится с итогом магазина; остатки точности распределения
сохраняются в последнем артикуле. Это представление в памяти, не дополнительные
проводки; переключатель способов распределения убран.
Распределение рекламы не выдаётся за её фактическую атрибуцию в Performance.

## Предварительная финальная версия 0.3.0 RC1

Оформление: белый фон, яркий синий, лимонный активный пункт меню, карточки в два
ряда. Под Ozon Profit — «ХОЧУ! Цацки» и логотип, подготовленный по изображениям
владельца. Manrope и Unbounded и их OFL-лицензии включены в static/fonts;
картинка — static/shop-logo.png. Все ресурсы включены в Windows ZIP и доступны
без внешней сети. Источники шрифтов: https://github.com/google/fonts .

Согласованные правила цветов магазина и артикулов:

- Прибыль > 0 зелёная, < 0 красная, ноль нейтрален.
- Реализация и начисления: не меньше прошлого сопоставимого периода — зелёные,
  меньше — красные. Даты и прежняя сумма доступны в подсказке.
- ДРР ≤ 10% зелёный; выше 10% красный.
- Доля чистой прибыли ≥ 25% зелёная; ниже красная.
- Стоимость, налоги, рекламная сумма и отсутствующие данные — нейтральные.

Текущий неполный месяц сравнивается с теми же днями прошлого (1–3 ноября с
1–3 октября), полный календарный месяц — с полным предыдущим. Скользящие окна
сохраняют число дней и заканчиваются месяцем раньше. Неполные/отсутствующие
данные сравнения не выдаются за нули. Подсказки показывают реальные даты.

В «Обзоре» оставлено только распределение общих расходов по выручке. Из «Товаров»
убраны колонка, история-флаг и галочка приблизительной себестоимости; новые
ручные значения точные. По подтверждению владельца имеющиеся значения приняты:
однократная миграция снимает флаг estimated, сохраняя все суммы, даты и заметки.
Правило стоимости по «Рыбе» и приоритет собственной цены сохраняются.
Пользовательские базы, ключи и финансовые файлы не включены в релиз.

## Проверяемый план продаж и количество штук — RC2

Цена плана — фактическая оплата покупателя после скидок (подтверждено владельцем).
Формула: реализация + предполагаемый соинвест − комиссия − логистика − прочие
услуги − себестоимость − реклама за клики − продвижение за заказы − налоги −
разовые расходы. Все статьи видны в отдельной сверяемой таблице, а также в
строках товаров. Комиссия = фактическая комиссия истории / реализация истории ×
плановая реализация. Логистика и другие услуги берутся на нетто-проданную штуку
(продажи минус возвраты) и умножаются на количество. Для своего артикула его
условия имеют приоритет, для нового — средние магазина. Общие комиссии
распределяются по реализации, общие логистика/услуги — по нетто-количеству.
Рекламные расходы исключены из этих средних, разовые компенсации не переносятся.
Возвраты комиссий/услуг уменьшают соответствующую статью, не начисляются второй раз.

Исторический соинвест можно исключить отдельной галочкой; по умолчанию он
учитывается, как в прежнем плане, но явно показан как условие будущего сценария.
Показана чувствительность прибыли без этих выплат при тех же удержаниях.
Выбранные 0% продвижения за заказы не превращаются автоматически в 6%.
Если плановый ДРР ниже исторического, показаны предупреждение и сравнительный
сценарий с прежним ДРР при тех же ценах/количестве/прочих расходах. Бюджет не
является прогнозом достижимого количества заказов. Дополнительные расходы и
налоги распределяются в строки так, чтобы прибыль строк сходилась с итогом.
Нет цели подогнать расчёт к конкретной желаемой прибыли на штуку.

В «Обзоре» добавлены продажи, возвраты и итоговое нетто-количество штук; в
товарной таблице — те же три колонки и показатели выбранного артикула.
Операции услуг, комиссии и физическое восстановление запаса не считаются новыми
продажами или повторными финансовыми возвратами. Возвраты прошлых продаж могут
дать отрицательное нетто-количество в текущем периоде. Средняя прибыль на штуку
показывается только при положительном нетто-количестве. Исходные денежные
операции, ключи, сохранённые цены, количество и рекламные настройки плана не
переписываются этой доработкой. Проверки используют вымышленные данные.

## Расходы на Ozon без рекламы — RC3

В общей и товарной сводках добавлен нейтральный процент:
(комиссия + логистика + упаковка + прочие услуги − соинвест) /
реализация покупателям после скидок и финансовых возвратов × 100%.
Источник — финансовые операции Seller, а не рекламный бюджет Performance.
Реклама, себестоимость, налоги, компенсации за товары и неклассифицированные
ручные корректировки не считаются услугами маркетплейса. Возвраты услуг снижают
числитель, отмены соинвеста увеличивают. Отрицательный результат не обрезается
до нуля: он означает превышение возмещений над платой за услуги. При нулевой
или отрицательной реализации процент не определяется; итоговые начисления без
детализации не выдаются за нулевые расходы. В подсказке показана сумма в рублях.

По артикулам общая часть распределяется по выручке по действующему правилу;
сумма расходов товаров сохраняет итог магазина. Новое поле — только аналитика:
оно не изменяет операции, прибыль, стоимость, налоги, ключи или сохранённый план.
Проверки покрывают соинвест, сторно, возвраты услуг, отсутствие положительной
реализации, исключение рекламы и распределение общих расходов. Синтетический
Windows smoke проверяет 12% одновременно для магазина и единственного артикула.

### Реклама и показы

В разделе «Реклама» выберите период и нажмите «Обновить аналитику».
На графике общие показы сопоставляются с расходами за клики и историей
продвижения «Оплата за заказ — все товары». Асинхронный отчёт Ozon может
потребовать дополнительного нажатия «Проверить готовность отчёта».
Если Seller API ограничивает доступ к показам, доступен импорт Excel/CSV
по шаблону. Загруженная история сохраняется между запусками.
Подробности источников и ограничений: [TRAFFIC_ANALYTICS.md](TRAFFIC_ANALYTICS.md).
